# Docs 结构与编写规范（spec.md）

> **用途：** 规定项目 Docs 的具体组织结构、必要文档及导航编写要求，供初始化和日常维护共同遵循。
> **依据：** `principles.md` 定义职责与组织原则；本文件将其落实为可检查的文档规格。`init.md`、`maintain.md` 分别决定何时、如何执行，不在本文规定操作流程或权限。

## 一、适用范围与约束级别

本文件约束项目中的 `docs/` 及其知识导航，不要求统一改造全部仓库文档。

- **必须：** 新建或维护相应内容时应满足的要求；不满足时需要说明原因。
- **默认：** 新项目采用的建议结构；已有项目可复用具备同等作用的内容，不为统一名称而迁移。
- **按需：** 只有存在实际内容或明确使用需求时才建立，不得为了补齐形式制造文档。

**规范是目标状态，不是自动改造授权。** 已有资料的迁移、重命名、删除、合并，以及大规模结构调整，应按 `init.md` 或 `maintain.md` 的权限边界执行；不能因发现格式不符就擅自整理。

## 二、目录与文档的基础规格

### 2.1 顶层结构

首次建立完整 Docs 工作区时，采用以下基础结构：

```text
项目根目录/
├── AGENTS.md
└── docs/
    ├── index.md
    ├── project/index.md
    ├── design/index.md
    ├── pending/index.md
    ├── evidence/index.md
    ├── rules/index.md
    ├── knowledge/index.md
    └── inbox/index.md
```

- **固定标识：** 顶层模块目录使用上述英文名称；`index.md`、`AGENTS.md` 保持固定名称。
- **不强制填充：** 未产生实际内容的模块可以只有索引；已有项目也不因使用了其他有效组织方式就强制迁移。
- **主题分层：** 同一模块内，相关内容增多后再建立主题子目录。不得预设大量空目录或机械照搬源码目录树。
- **一个主要来源：** 资料已经存在且可靠时，优先链接原件；不为满足目录归属制造内容副本。

### 2.2 文件与资源位置

- 内容文档默认使用简洁、能表达主题的**中文名称**；技术专名、协议、代码符号和已有约定可保留英文。
- 不强制文件名添加日期、编号或模块前缀。只有为区分版本、历史方案或同名主题所必需时才添加。
- 文档必要的配图或附属资源，默认放在文档旁的同名 `.assets/` 目录，并采用可理解的资源名称。**资源目录不是知识目录，不必为图片逐级编写知识导航。**
- 不在 `docs/` 保存源码、配置或外部契约的无必要副本；这些资料可在原位置保存，由相关文档提供链接。确需保存原件时应能说明用途及来源。
- 正文不要求统一章节模板，按内容选用文字、表格、图示和代码片段；事实、计划与推测应能区分。

## 三、`index.md` 知识索引与导航规范

### 3.1 核心定位

`index.md` **是所在知识范围的认知入口与导航中心。**

它不仅用于列出文档，还应提供理解当前知识范围所需的基本信息，帮助人和 AI 建立整体认识、理解内容组织及重要关系，并根据实际任务逐步定位相关文档、依据和实现。

每个 Docs 知识目录必须包含 `index.md`。

索引遵循以下原则：

1. **信息优先：** 索引的价值取决于信息的准确性、完整性和实用性，结构、格式与篇幅均服务于信息表达。
2. **认知与导航并重：** 既让读者理解当前范围，也帮助读者找到需要进一步阅读的内容。
3. **逐层抽象：** 每级索引提供当前层次所需的整体认识，并通过下级索引、具体文档或代码逐步深入。
4. **关系明确：** 不仅说明有哪些内容，还应根据需要表达内容之间的组成、依赖、协作、演变及其他重要关系。
5. **按需组织：** 根据实际知识结构选择文字、表格、列表或图示，不强制统一模板。
6. **避免无效重复：** 可以概括重要知识，但不应为了完整而复制下级文档的大量细节。

**索引本身允许直接承载有价值的知识，不必将所有信息都拆成独立文档。**

### 3.2 索引应提供的信息

索引应根据所在目录的实际情况，提供以下信息。

| 信息维度             | 内容要求                                                                     |
| -------------------- | ---------------------------------------------------------------------------- |
| **定位与范围** | 说明当前知识范围是什么、主要解决什么问题，以及必要的内容边界。               |
| **整体认识**   | 概括当前范围内的重要事实、概念、能力或主题，使读者能够建立基本理解。         |
| **组成与组织** | 说明主要内容由哪些部分组成、如何分组或分层，以及组织这些内容的依据。         |
| **重要关系**   | 说明各部分之间具有理解价值的依赖、协作、关联或演变关系，必要时提供简要图示。 |
| **内容导航**   | 提供实际存在的文档、子目录或相关资料入口，并说明其具体内容。                 |
| **使用场景**   | 说明不同资料适用于哪些问题、任务或阅读目的，帮助读者选择入口。               |
| **深入路径**   | 指明从当前认识继续深入到具体主题、实现细节、代码或原始依据的路径。           |
| **状态与限制** | 对影响正确使用的版本、适用条件、有效状态、未解决问题或已知限制进行说明。     |
| **关联资料**   | 在存在重要关联时，提供相关设计、规则、知识、证据或外部资料的入口。           |

以上是**信息维度，不是固定章节清单**。

具体要求：

* 与当前目录有关的信息应清楚表达，不为了满足表格项目而编造内容。
* 简单目录可以将多项信息合并在几段文字中。
* 复杂目录应充分表达整体结构、主要关系和查找路径，不因追求简短而省略重要信息。
* 不存在相关内容时，可以省略对应维度，不要求逐项声明“无”。
* 空目录只需说明用途和当前状态，无需生成虚假的导航或知识内容。

### 3.3 内容组织与表达要求

#### 3.3.1 先建立认识，再提供深入路径

索引应尽量让读者在深入具体文档之前，对当前范围形成必要认识。

例如：

* Project 索引可以概括系统组成、主要职责和关键协作关系。
* Design 索引可以概括当前涉及的主要设计问题及其关联。
* Knowledge 索引可以介绍知识主题之间的联系和必要背景。
* Rules 索引可以说明规则体系、适用范围及查找方式。

不要求所有索引采用相同的介绍方式。

**读者能够从当前索引直接获得的信息，不必为了形式上的分层而强制跳转到另一份文档。**

但当某项内容需要详细论述、独立维护或被多处引用时，应考虑使用独立文档，并从索引提供入口。

#### 3.3.2 表达内容之间的关系

索引不应将实际存在关联的内容简单处理为互不相关的文件列表。

当关系有助于理解或查找时，应予以说明，例如：

* 系统组成部分之间的职责与协作关系。
* 功能模块之间的依赖、调用或数据流。
* 设计问题之间的关联、继承或替代关系。
* 知识主题之间的前置概念和相互联系。
* 规则与其适用对象之间的关系。

可以使用文字、表格、列表或 Mermaid 图表达。

图示应具有明确的信息价值，与实际资料保持一致。**不要求每份索引必须有图，也不为了美观重复绘制已有内容。**

#### 3.3.3 提供面向任务的导航

导航应帮助读者根据目的选择资料，而不只是展示文件结构。

每个主要导航目标应具备：

| 信息                 | 要求                                                   |
| -------------------- | ------------------------------------------------------ |
| **名称与链接** | 使用准确、可识别的名称，指向真实存在的文件或目录索引。 |
| **内容摘要**   | 说明目标资料实际包含什么，突出主要内容和信息价值。     |
| **使用场景**   | 说明什么情况下需要阅读，尽量使用明确的任务或问题描述。 |

**内容摘要与使用场景必须有所区别。**

例如：

* 内容摘要：说明扫描调度机制、事件领取顺序及批次提交过程。
* 使用场景：排查扫描时序问题、调整调度逻辑或分析并发行为时阅读。

对于复杂目录，还应根据需要提供常见任务入口或推荐阅读路径。

导航可以按照主题、职责、业务流程、任务场景等自然组织，不要求全部采用表格。

#### 3.3.4 保持信息的适用性

当资料的状态或条件可能影响读者判断时，索引应提供必要说明。

例如：

* 当前使用、已停用或仅供历史参考。
* 已实现、规划中、探索中或尚未确认。
* 适用的版本、环境或使用条件。
* 已知问题、限制或需要进一步核实的内容。

状态信息应有事实依据，不得根据文件名、时间或目录位置擅自推断。

不要求为所有文档建立统一状态字段，只在确有必要时标注。

### 3.4 分层导航与索引分工

Docs 通过多级索引组织知识，但**分层依据是理解与使用的需要，而不只是文件系统的目录层级**。

#### 根索引：`docs/index.md`

作为整个项目 Docs 的总入口，应帮助读者：

* 了解当前项目及 Docs 工作区的基本情况。
* 理解已有知识主要分布在哪些范围。
* 发现重要主题及其相互关联。
* 根据常见任务快速找到合适的知识入口。
* 了解其他重要资料来源及其位置。

根索引可以提供必要的项目背景和整体关系，但不应机械复制所有下级索引，也不代替 Project 对项目本身的持续描述。

#### 模块索引：`docs/<模块>/index.md`

作为特定知识模块的入口，应帮助读者：

* 理解该模块在**当前项目**实际承载的知识。
* 了解主要主题、内容组织及重要关系。
* 根据问题或任务选择具体资料。
* 发现相关模块及进一步深入的路径。

模块索引重点介绍实际内容，不需要重复插件级原则文档中的完整模块定义。

#### 主题索引：各下级目录的 `index.md`

作为具体主题或知识分组的入口，应帮助读者：

* 理解当前主题的范围与必要背景。
* 认识该主题的主要组成、内容及关系。
* 找到具体知识、技术细节或实现位置。
* 根据不同需求选择合适的阅读路径。

主题目录可以按需要继续分层，不限制深度。

#### `AGENTS.md`

`AGENTS.md` 负责引导 Agent 进入 Docs，并按照当前任务按需阅读和使用相关知识。

它不应复制索引内容，也不承担替代索引进行完整知识导航的职责。

### 3.5 导航的组织方式

#### 按实际内容组织

索引应反映真实的知识组织，而不是为了保持目录整齐而强制分类。

对于内容较少的目录，可以直接提供整体说明和文档入口。

对于内容复杂的目录，可以先介绍主要组成及关系，再按主题、功能或任务组织导航。

当一组内容形成独立且稳定的知识范围时，可以建立下级目录；不要求每个主题都单独建立目录。

#### 支持多种查找路径

同一份资料可以在不同任务入口中被引用。

例如一份模块关系文档，可能同时适用于：

* 初次了解系统架构。
* 定位功能实现。
* 分析跨模块调用。
* 评估重构影响。

允许多个入口指向同一份资料，**但应避免为了不同导航场景复制多份正文。**

#### 保留必要的跨范围关联

当当前知识与其他模块或外部资料有直接关系时，应提供适当入口。

例如：

* Project 中引用相关 Design，解释重要设计决策。
* Design 中关联实际 Project，核对设计实现情况。
* Rules 中链接相关 Knowledge，帮助理解规则依据。
* Project 中链接外部接口契约，说明依赖的资料来源。

是否建立关联取决于实际用途，不要求为所有文档建立完整的双向引用网络。

#### 导航至有效位置

* 链接应指向实际存在且可访问的目标。
* 优先使用适合当前仓库的相对路径。
* 引用跨目录资料时优先链接原件。
* 修改文件位置后，应检查并修正受影响的导航。
* 不得虚构尚未存在的目标文件或内容。
* 已失效资料若仍有参考价值，应明确其状态及可用替代入口。

### 3.6 索引示例

以下示例仅说明信息组织方式，不规定固定模板。

```
# Project · 项目认知

## 项目概况

本项目负责接收外部输入，执行解析与校验，
生成处理结果并向相关系统提供查询或上报能力。

主要功能由输入接入、业务处理和结果输出组成。

## 主要组成与关系

输入接入 → 解析与校验 → 结果生成 → 查询或上报

- 输入接入：负责接收文件、消息或接口请求。
- 解析与校验：负责数据解析、业务检查及结果判定。
- 结果输出：负责结果组织、持久化和对外提供。

以上为主要逻辑关系，具体模块依赖及实现位置
参见《项目结构与代码位置》。

## 按任务查找

| 任务 | 入口 | 说明 |
| --- | --- | --- |
| 初次了解项目 | [项目总览](项目总览.md) | 了解系统目标、主要能力与组成 |
| 定位功能代码 | [项目结构与代码位置](项目结构与代码位置.md) | 查找模块职责、源码目录和关键入口 |
| 排查校验问题 | [解析与校验](解析与校验/index.md) | 了解处理流程、判定逻辑和相关实现 |
| 修改对外接口 | [对外接口](对外接口/index.md) | 查找当前接口能力、契约和实现位置 |

## 相关资料

- [设计方案](../design/index.md)：了解需求、方案及决策依据。
- [项目规则](../rules/index.md)：查阅开发和维护约定。

## 注意事项

本目录描述当前实际实现，不将尚未落地的设计
视为已有功能。修改实现前应核对实际代码。
```

该示例同时提供整体认识、组成关系、任务导航及关联入口。

实际编写时，可以采用更简洁或更详细的形式，**不要求照搬上述章节和表格**。

### 3.7 索引质量检查

索引的质量应根据实际阅读和查找效果判断，而不是根据篇幅、标题数量、表格数量或链接数量判断。

检查时重点关注：

1. **能否建立认识？** 读者是否能够理解当前范围是什么、包含什么，以及主要内容如何组织？
2. **能否理解关系？** 对理解和使用有影响的重要组成、依赖或关联是否得到表达？
3. **能否按任务查找？** 读者是否能够根据具体问题选择合适的资料入口？
4. **能否逐层深入？** 是否能够从当前索引继续找到必要的细节、代码或依据？
5. **信息是否真实？** 摘要、关系、状态及链接是否与实际内容一致？
6. **是否存在无效重复？** 索引是否重复维护了大量不必要的正文，增加更新成本？
7. **组织是否自然？** 是否出现为了遵循格式而拆分、堆砌或遗漏重要信息的情况？

对复杂知识范围，可以采用实际任务进行验证，例如让不了解项目的人或 Agent 通过索引完成项目理解、功能定位或问题排查。

如果索引无法支持有效理解与查找，应优先补充缺失的信息、关系和导航，而不是仅调整排版。

**最终要求：**`index.md` **应让人和 AI 在当前层级获得足够的认识，并能够以较低成本找到下一步所需的信息。信息是目的，结构是载体。**


## 四、Project 的内容规格

**Project 应建立与实际实现一致的项目认知，使人和 AI 能够从整体到局部理解当前系统，并根据需要定位具体代码。**

Project 不仅描述项目的文件结构，还应说明项目的能力、行为、职责划分及重要关系。

**信息覆盖是要求，文档划分是手段。** 不强制使用固定文档数量、名称或层级。

### 4.1 应覆盖的核心信息

根据项目实际情况，Project 应能够提供以下信息：

| 信息维度                 | 内容要求                                                           |
| ------------------------ | ------------------------------------------------------------------ |
| **项目定位**       | 项目解决什么问题、提供什么能力、承担什么职责，以及必要的系统边界。 |
| **整体组成**       | 主要工程、子系统或逻辑模块如何划分，各自承担什么职责。             |
| **功能与行为**     | 主要功能如何工作，重要业务流程和关键处理机制是什么。               |
| **协作与关系**     | 模块之间的重要调用、依赖、数据流及外部系统交互。                   |
| **代码定位**       | 逻辑功能与实际代码、配置及关键入口之间的对应关系。                 |
| **当前状态与限制** | 已实现的能力、实际存在的限制，以及影响理解和使用的已知问题。       |

以上信息应根据项目规模和实际需要进行组织，不要求每个维度都单独成文。

对尚无实际实现的新项目，不得编造项目结构、功能行为或代码位置；已有实现但尚未核实的内容，应明确其不确定性。

### 4.2 分层认知与内容组织

**以项目的实际组成与行为为基础，从整体到局部逐步展开。**

#### 项目入口

`project/index.md` 应作为当前项目的认知入口。

根据项目复杂度，可以直接介绍：

* 项目的基本情况和主要能力。
* 主要组成部分及职责。
* 重要模块之间的关系或关键业务流程。
* 当前范围内值得了解的限制。
* 进一步理解功能、结构和代码的导航入口。

可以使用简要结构图、流程图、表格或文字表达，不要求固定格式。

**索引允许直接承载必要的项目知识，不应为了满足文档结构而将完整、简短的信息强行拆分。**

#### 深入组织

当项目内容超出当前索引适合承载的范围时，再按实际需要建立独立文档或下级主题。

常见的组织对象包括：

* 项目整体架构与组成。
* 子工程、子系统及其职责。
* 重要功能模块。
* 关键业务流程与处理机制。
* 接口、数据流及跨模块协作。

各层级应能够说明当前范围的主要内容，并指向进一步深入的资料。

不强制与物理代码目录一一对应，也不规定固定分层深度。

### 4.3 项目结构与代码定位

**Project 应建立项目认知与实际代码之间的联系，使读者能够从功能和职责定位实现。**

对于已有代码的项目，应提供有效的代码导览能力。

至少能够帮助读者回答：

1. **在哪里？** 相关功能或模块对应哪些实际工程、目录或代码入口？
2. **负责什么？** 这些位置承担什么职责、提供什么能力？
3. **如何协作？** 与哪些模块发生重要调用、依赖或数据交互？
4. **如何深入？** 需要理解或修改具体行为时，应继续查阅什么？

代码导览可根据需要包含：

* 主要工程与重要目录的职责说明。
* 逻辑模块与实际路径的对应关系。
* 关键类、接口、配置及程序入口。
* 重要调用链、数据流或模块依赖。
* 跨工程功能的实现位置及关联入口。

示例：

```
| 功能 / 模块 | 主要职责 | 实现位置 | 关键关系 |
| --- | --- | --- | --- |
| HTTP 接入 | 接收并分发请求 | `src/api/` | 调用业务服务 |
| 业务处理 | 执行核心业务逻辑 | `src/services/` | 访问数据层 |
```

路径必须来源于实际项目，不得使用推测或示例路径描述真实实现。

不应以完整文件树代替功能导览，也不要求逐行解释代码。

代码导览可以直接包含在项目索引、相关模块索引或独立文档中。项目复杂时，可建立专门的结构与代码导览文档；项目简单时，无须额外拆分。

### 4.4 内容之间的关系

**Project 应表达项目组成部分如何形成一个实际运行的整体，而不是孤立介绍各个模块。**

当关系对理解和定位具有实际价值时，应予以说明。

例如：

* 功能从哪个入口开始，经过哪些主要处理环节。
* 不同模块分别承担哪些职责，如何交换数据。
* 本项目如何调用外部服务，以及如何处理响应与异常。
* 某项功能由哪些工程共同完成。
* 关键配置如何影响实际行为。

可以使用文字、表格、流程图或结构图。

对于复杂关系，可以在上层索引概括主要链路，再链接下级文档说明细节。

**关系描述应以实际实现为依据，不得将预期架构或尚未实现的设计当作当前系统行为。**

### 4.5 文档划分与维护边界

#### 文档划分

* 优先利用现有内容，不因推荐名称而创建重复文档。
* 同一主题内容能够清楚表达时，不强制拆分。
* 不同主题具有独立理解和维护价值时，可以分开组织。
* 重要内容可以在上层索引中概括，详细信息在下级文档中维护。
* 同一事实尽量保留一个主要维护位置，其他位置通过摘要和链接关联。

`项目总览.md`、`项目结构与代码位置.md` 可以作为推荐名称，但不是强制文件，也不是 Project 初始化的固定完成条件。

#### 内容边界

* **当前事实：** 以实际代码、配置和可核实行为为依据。
* **设计意图：** 尚未实现的方案及决策依据由 Design 承载，Project 可提供关联入口。
* **外部资料：** 外部接口契约等资料可以保留原件并建立引用；Project 重点说明本项目如何实际使用相关能力。
* **历史内容：** 已停用或被替代的实现应与当前有效内容明确区分。
* **开发过程：** 不将每次修改记录、实现步骤或临时工作日志作为 Project 的主要内容。

项目演进时，应修正受到影响的现状描述、关系和代码位置，不以不断新增文档代替对已有知识的维护。

### 4.6 Project 的质量要求

检查 Project 时，应重点判断：

1. 读者能否理解项目当前具备哪些主要能力？
2. 能否理解项目的重要组成部分及其职责？
3. 能否理解主要功能如何运行、各部分如何协作？
4. 能否从逻辑功能找到真实代码位置和关键入口？
5. 能否根据当前问题沿索引逐步深入相关内容？
6. 文档是否真实反映当前实现，并区分规划、历史和未核实的信息？
7. 是否存在明显的重复、断裂或无法使用的导航？

**最终要求：Project 应当成为真实项目在 Docs 中可理解、可导航、可持续修正的知识映射，而不是源码目录清单或文档集合。**

## 五、其他模块的内容规格

除 `index.md` 的统一导航要求外，其余模块**不设置强制正文模板**，仅约束必要信息和组织边界：

| 模块                | 内容组织要求                                                                                                   |
| ------------------- | -------------------------------------------------------------------------------------------------------------- |
| **Design**    | 以设计问题为单位组织；让当前结论、候选方案、未定事项和重要演变可辨。允许不完整与矛盾，不要求统一状态目录。     |
| **Pending**   | 简单事项可用清单，复杂事项可独立成文；明确待做事项及必要进展，不建立已完成任务档案。                           |
| **Evidence**  | 按验证活动或对象临时组织；说明验证对象、条件、结果和证据位置。正式测试代码仍在源码工程，临时证据默认不入 Git。 |
| **Rules**     | 每条规则或规则组应能识别适用场景、范围、具体要求和约束程度；相同规则避免多处独立维护。                         |
| **Knowledge** | 按概念、问题、方法或经验主题组织；短技巧与长笔记均可存在，未确认的理解应标明不确定性。                         |
| **Inbox**     | 仅作为未分类内容容器；不规定统一格式，不要求定期清空或强制流转。                                               |

默认的“**代码注释优先中文，专业术语等除外**”是项目的 **Rules 内容**，由初始化指南负责创建或核对；不应把这条项目约定混入插件的通用目录结构定义。

### 5.1 Design 的参考资料

**Design 可以按需建立 `docs/design/参考资料/`，集中存放或索引支撑项目需求分析、方案设计及技术对接的原始依据。** 这是 Design 的可选子目录，不新增顶层模块；没有相关资料时不必创建。

适合收纳或索引的内容包括：

* 外部系统提供的接口契约、OpenAPI 描述、报文格式和协议约定；
* 需求原件、业务规范、设计约束及第三方技术说明；
* 为特定设计问题保留的其他来源资料。

该目录应遵循以下要求：

1. **按用途判断，而非按文件类型归类。** 直接作为本项目需求、设计或对接依据的资料，可以放在 Design 的参考资料区；并非所有接口文档、配置说明或外部资料都必须放入这里。
2. **区分依据与结论。** 原始契约或需求资料是设计输入，不等同于本项目的设计决策；具体方案、取舍及其理由仍按设计问题组织。
3. **区分参考与实现。** 本项目实际提供、调用接口的行为、处理流程及代码位置，应在 Project 中能够找到；参考资料不能代替对当前实现的描述。
4. **不挤占 Knowledge。** 以技术学习、原理理解或可借鉴经验为主要目的的内容仍属于 Knowledge；不能仅因为一份资料来自外部，就自动归入 Knowledge 或 Design。
5. **保留原件，避免重复。** 原件已存在于 `需求/`、其他工程目录或可信来源时，可以通过索引链接原件；不要求复制或迁移。确需在参考资料区存放副本时，应说明来源、版本或适用性。
6. **提供导航。** 创建 `参考资料/` 后，应有 `index.md`，按实际用途组织资料，说明内容摘要、使用场景以及必要的来源、版本、有效性或关联设计。

例如：外部平台的《取图接口契约》可放在 `design/参考资料/接口契约/` 或保持原位置并被该目录索引引用；本项目的《取图接入方案》仍属于 Design 的设计内容；已经实现的调用与错误处理属于 Project。

**此规格只明确允许的组织方式，不构成迁移授权。** 已在 Knowledge、Project 或其他目录中的现有资料，不得仅为统一分类而自动搬迁；调整时遵循 `init.md` 或 `maintain.md` 的执行权限。

默认的“**代码注释优先中文，专业术语等除外**”是项目的 **Rules 内容**，由初始化指南负责创建或核对；不应把这条项目约定混入插件的通用目录结构定义。

## 六、规格检查要点

检查已有文档或审阅新建结果时，关注可验证的内容，不以外观整齐替代质量：

- [ ] `docs/index.md` 可达，实际知识目录有导航入口；`AGENTS.md` 指向正确的 Docs 根索引。
- [ ] 导航链接有效，每个实际导航条目有**内容摘要与使用场景**，二者不重复。
- [ ] 已有代码的项目有可找到的**项目总览**和**代码位置导览**（可复用等效资料）；路径与实际实现一致。
- [ ] 文档名称清晰，普通内容文档中文优先；没有为统一命名批量重命名已有资料。
- [ ] 没有为了分类产生不必要的资料副本、空文档或额外目录层级。
- [ ] 已实现的项目事实、设计意图、临时证据和长期规则没有混成未经说明的同一种结论。

**符合规格不等于获得修改授权。** 具体创建、迁移、更新及是否需要人工确认，始终由 `init.md` 或 `maintain.md` 按当前任务决定。
