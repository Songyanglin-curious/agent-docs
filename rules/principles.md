# Docs 初始化操作指南（init.md）

> **用途：** 指导当前 Agent 在新项目中建立 Docs，或将已有项目接入 Docs。
>
> **依据：** 初始化前应阅读 [Docs 组织原则](principles.md) 和 [Docs 结构与编写规范](spec.md)。
>
> * [principles.md](principles.md)：明确 Docs 的组织原则、模块职责及内容边界。
> * [spec.md](spec.md)：明确目录结构、索引导航、文档内容及编写要求。
>
> 本文负责规定初始化步骤、执行权限和验收要求，不重复定义上述规范。
>
> **触发：** 仅在用户明确要求初始化、接入或改造 Docs 时执行；日常结束 Hook 不运行本指南。

## 一、执行目标与边界

初始化完成后，应达到以下结果：

1. 人和 AI 能从项目 `AGENTS.md` 找到 `docs/index.md`，再按索引找到需要的知识；导航内容符合 [索引规范](spec.md#三indexmd-知识索引与导航规范)。
2. 项目已有的有效知识能够被找到和利用；已有代码的项目应按照 [Project 内容规格](spec.md#四project-的内容规格)，建立基于实际实现的项目认知与代码导航。
3. Docs 的组织方式符合 [principles.md](principles.md)，目录、索引、文档内容及命名符合 [spec.md](spec.md)，且不破坏既有资料。

**不以“所有旧文件都搬进标准目录”“每个模块都有内容”“生成大量文档”为完成条件。** 初始化不是全面重写文档，更不是日常维护或知识归档。

用户只是询问初始化方案、分类意见或改造建议时，**只分析并回答，不执行文件修改**。

## 二、导航与表达规范

### 2.1 导航层级

使用以下导航关系：

`AGENTS.md → docs/index.md → 各级 index.md → 具体文档`

- **`AGENTS.md`：** 为 Agent 提供 Docs 入口和基本查阅指引。只保留必要的全局导航；不重复列出全部文档或复制具体规则。
- **`docs/index.md`：** 说明当前项目的 Docs 内容与组织情况，是项目知识的总入口，不代替 Project 描述项目实现。
- **目录 `index.md`：`index.md` **是所在知识范围的认知入口与导航中心。它不仅帮助人和 AI 找到资料，还应提供理解这些资料所需的基本背景、整体结构、关键关系和阅读路径，使读者能够逐层建立认识，并定位需要深入的内容。
- **具体文档：** 承载知识内容，不依赖阅读整套 Docs 才能理解其主要含义。

**每个实际存在的 Docs 目录都应有 `index.md`。** 空目录可以只有用途说明，不需要虚构导航条目。

### 2.2 命名与表达

- 普通内容文档**优先采用简洁、准确的中文文件名**，直接表达主题；专业术语、产品、协议和代码标识符可以保留英文。
- 约定的目录标识及特殊文件名（如 `project/`、`index.md`、`AGENTS.md`）保持稳定，不为中文化而修改。
- 不强制添加日期、编号或模块前缀；仅在区分版本、时间或同名主题确有必要时使用。
- 文档以清晰、可查阅为优先，按内容选用文字、表格、示意图和代码示例，不统一规定正文模板。
- 原始代码、运行配置、外部资料已有可靠来源时，优先通过链接引用；避免在 Docs 中维护容易过期的冗余副本。必要配图及附件可以随文档就近组织。

## 三、模块职责（6+1）

六个基本功能模块加一个兜底容器，是 Docs 的初始分类基准。模块不是强制工作阶段，也不要求每个项目都填充全部模块。

| 模块                | 核心职责                                             | 主要回答的问题                                         |
| ------------------- | ---------------------------------------------------- | ------------------------------------------------------ |
| **Project**   | 描述实际项目当前的组成、能力、行为、关系及已知限制。 | 项目现在是什么样？各部分做什么、怎样协作、代码在哪里？ |
| **Design**    | 承载需求、设计问题、方案、决策依据及有价值的演变。   | 为什么做？准备怎么做？为何这样选择？后来有什么变化？   |
| **Pending**   | 保存当前仍需处理的工作事项。                         | 还要做什么？目前进展怎样？                             |
| **Evidence**  | 临时存放测试、实验、验收、审查等验证材料。           | 验证了什么、怎么验证、结果和依据是什么？               |
| **Rules**     | 保存持续适用的规范、约定、约束和偏好。               | 在什么场景下、什么范围内，应遵循什么要求？             |
| **Knowledge** | 积累以人的理解和学习为主、也供 AI 查阅的知识与经验。 | 这是什么？有什么用？有什么条件与局限？                 |
| **Inbox**     | 容纳暂时无法确定归属的内容。                         | 这份暂时未分类的资料先放在哪里？                       |

### 3.1 Project：真实项目的知识映射

**Project 描述当前实际存在的项目，而不是预期中的项目。**

- 以代码、配置、可确认的运行行为为依据，描述组成、职责、能力、重要关系及已知限制。
- 从整体到局部组织内容，优先说明职责与协作，再在必要处深入实现细节；不机械复制源码目录树。
- 同时保留逻辑功能与实际代码位置之间的对应关系，便于人和 AI 逐层定位。
- 随实现变化修正当前描述，不把每次开发操作追加成历史流水账；尚未实现的方案不能写成既有能力。

### 3.2 Design：设计问题与决策认识

**Design 以设计问题为组织单位，保存项目为何以及如何发展。**

- 容纳需求、背景、约束、候选方案、决策依据和重要设计演变；不强制按模块、时间或状态分类。
- 允许想法不完整、结论未定、方案并存甚至相互冲突，但应让读者辨认当前结论、分歧和不确定点。
- 保留有价值的取舍及原因，不要求保存每轮讨论；设计被实施或替代，也不必自动删除其历史价值。
- 简单问题可以独立成文；复杂问题按实际需要拆分并相互引用，不强制固定流程和文档模板。

### 3.3 Pending：仍需执行的工作

**Pending 只管理当前还有行动需求的事项。**

- 内容围绕待办目标、必要背景、当前进展与完成条件展开，简单事项无需详细模板。
- 可以用清单或独立文档组织，按主题自然分组；不要求所有简单任务都进入 Pending。
- 事项完成、取消、被替代或不再需要执行时，即退出 Pending；不以 Pending 保存完成历史或成果记录。
- 未决定执行的设想属于 Design 等其他模块，不因为“以后可能做”就自动成为待办。

### 3.4 Evidence：临时验证工作区

**Evidence 保存近期验证活动的证据，不承担永久知识归档。**

- 按验证活动或对象组织报告、截图、日志及必要条件，区分已验证、未验证与验证失败的内容。
- 临时验证材料默认不进入 Git；固定索引可以纳入版本管理。正式测试代码、测试用例和长期维护的夹具仍归属代码工程。
- 证据应有可清理的边界，避免无限积累；具体保留时限和清理动作由维护规则或项目约定决定。
- 具有长期价值的结论应进入对应知识模块，而非依靠永久保留整套临时证据。

### 3.5 Rules：持续适用的约定

**Rules 是人和 AI 在项目中共同遵循的行为依据。**

- 保存可反复适用的规范、约定、约束及稳定偏好，不保存仅对单次任务有效的指令。
- 一条规则应能辨认适用场景、要求内容、适用范围及约束程度（强制、默认约定或偏好）。
- 以规则或主题自然组织，不强制按项目模块划分；相同规则尽量只有一处主要维护位置。
- 规则与实践或其他规则发生冲突时，应明确其适用条件，避免多份相互矛盾的有效约定并存。

### 3.6 Knowledge：面向人的知识积累

**Knowledge 是以人的理解和积累为主、同时供 AI 使用的知识空间。**

- 保存知识原理、技术方法、工程技巧、实践经验及值得保留的研究认识；不要求直接对应当前项目或跨项目通用。
- 以知识主题为基本组织单位，可以围绕概念、问题、方法或经验展开；相关内容增多后再自然分层。
- 允许短技巧、长篇笔记和不成熟的认识并存，不强制统一格式；应区分事实、个人理解和推测。
- 注重内容能否被理解、找到和复用，不要求每份知识都形成明确结论或立即指导开发。

### 3.7 Inbox：未分类内容容器

**Inbox 仅为暂时无法确定归属的内容提供存放位置。**

- 允许不同主题、形式和成熟程度的内容共存，不强制立即分类。
- 不承担额外的筛选、加工、归档或任务管理职责。
- 归属明确后可以迁出；不要求定期清空，也不应把它作为无差别保存所有对话内容的入口。

## 四、容易混淆的职责边界

| 情形                     | 归属原则                                                                                                                                           |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| 设计方案与实际实现       | **Design** 说明目标、方案和原因；**Project** 说明当前真实实现。两者可关联，但不能互相替代。                                            |
| 已决定的需求与具体待办   | **Design** 保存需求及决策依据；**Pending** 只保存仍需跟踪和执行的事项。                                                                |
| 工程方法与项目约定       | **Knowledge** 解释方法、原理和适用条件；确立持续性要求后，**Rules** 记录应如何遵循。                                                   |
| 验证证据与长期结论       | **Evidence** 存近期验证材料；长期有效的项目事实、设计认识或技术经验分别归入 **Project、Design、Knowledge** 等。                        |
| 外部接口契约与本项目集成 | 外部契约原件可保留在其来源位置或作为参考资料索引；**Project** 描述本项目实际如何依赖、调用和处理接口。不能仅依据“谁维护这份文件”判断归属。 |
| 暂时无法判断的资料       | 内容确实需要保存、但当前无法确定归属时，可暂放**Inbox**；不为强行分类扭曲含义。                                                              |

**归属取决于文档实际描述的对象，而不是文件名称、产生阶段或所属人员。** 同一事项可能涉及多个模块，但各模块只表达自己负责的那一面，其他信息通过引用关联。

## 五、原则与操作指南的分工

- **`principles.md`**：定义 Docs 应如何组织、各模块承担什么职责、内容与导航应达到什么要求。
- **`init.md`**：规定新项目或已有项目怎样建立、接入和检查 Docs，包括必要模板与操作边界。
- **`maintain.md`**：规定日常工作后怎样判断是否需要维护，以及如何创建、更新、整理和确认具体修改。

这三份文件属于插件级通用规则，不要求在每个项目重复保存。项目自己的 `docs/` 存放实际知识与导航，`docs/rules/` 存放项目适用的规则，而不是插件自身的运行说明。

**总原则：分类为理解服务，索引为查找服务，文档为人和 AI 的持续认知服务；不为了符合目录形式而牺牲实际可用性。**
