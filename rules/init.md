# Docs 初始化操作指南（init.md）

> **用途：** 指导当前 Agent 在新项目中建立 Docs，或将已有项目接入 Docs。
> **依据：** 先读取插件级 `principles.md`。本文只规定初始化操作、必要模板、权限边界和验收要求，不重复定义各模块职责。
> **触发：** 仅在用户明确要求初始化、接入或改造 Docs 时执行；日常结束 Hook 不运行本指南。

## 一、执行目标与边界

初始化完成后，应达到以下结果：

1. 人和 AI 能从项目 `AGENTS.md` 找到 `docs/index.md`，再按索引找到需要的知识。
2. 项目已有的有效知识能够被找到和利用；已有代码的项目应有**基于实际实现**的 Project 入门说明。
3. 目录、索引、初始规则和临时证据处理方式符合 `principles.md`，且不破坏既有资料。

**不以“所有旧文件都搬进标准目录”“每个模块都有内容”“生成大量文档”为完成条件。** 初始化不是全面重写文档，更不是日常维护或知识归档。

用户只是询问初始化方案、分类意见或改造建议时，**只分析并回答，不执行文件修改**。

## 二、先检查，再决定做什么

在修改任何文件前，完成以下检查；只读取与判断初始化有关的材料，不要求通读整个仓库。

| 检查项   | 实际动作                                                                    | 需要得到的结果                                                 |
| -------- | --------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 项目边界 | 确定项目根目录、主要子工程、代码与配置位置。                                | 知道 Docs 应服务哪个项目；不误操作上层或其他仓库。             |
| 版本管理 | 检查 Git 根目录、工作区已有改动及 `.gitignore`；非 Git 项目确认实际情况。 | 知道哪些文件已有修改，避免覆盖或误提交。                       |
| 既有导航 | 查找并阅读根 `AGENTS.md`、已有 `docs/index.md` 和相关子项目入口。       | 确认已有导航与项目指令，避免重复或冲突。                       |
| 现有资料 | 盘点 `docs/`、子工程文档、README、需求、技术资料及其他被明确指定的来源。  | 区分仍在使用的资料、重复副本和可能过时的记录；不凭路径猜内容。 |
| 真实项目 | 对有代码的项目，按需检查项目入口、主要工程及关键调用关系。                  | 为 Project 概览找到足够的事实依据；不能确认的内容不编造。      |

根据检查结果选择路径：

- **A．尚无 Docs、也无实际实现：** 建立基础导航与空模块索引，不虚构项目结构。
- **B．已有实现、尚无可用 Docs：** 建立基础导航，结合代码及已有资料补充最小 Project 概览。
- **C．已有 Docs：** 先判断现有索引能否正常使用；以**接入、增补和修复缺口**为主，保留有效结构与内容。

如果 Docs 已能满足上述目标，**不重复初始化**；仅处理明确的缺口并结束。

## 三、确定本次操作范围

执行前形成一份简短的变更清单，至少明确：

- **新建：** 需要新增哪些目录、索引或初始文档；
- **增补：** 哪些已有索引、`AGENTS.md` 或规则需要补充；
- **复用：** 哪些现有资料保留原位，通过链接纳入导航；
- **待确认：** 哪些调整可能影响已有内容或既有约定。

按以下权限处理，**不要把“用户要求初始化”理解为可以任意整理仓库**：

| 操作                                               | 处理方式                                               |
| -------------------------------------------------- | ------------------------------------------------------ |
| 创建缺失的基础目录、索引和导航                     | 在本次初始化授权范围内直接执行。                       |
| 增补 `AGENTS.md` 的 Docs 入口、补充不冲突的索引  | 先读取原文，最小增量修改，避免重复。                   |
| 根据已核实的代码建立最小 Project 概览              | 可以执行；只写可确认事实，未核实处不猜测。             |
| 发现现有资料位置不符合新分类                       | **优先建立引用**，不以分类为由直接移动。         |
| 移动、重命名、合并、覆盖或删除既有资料；重组原目录 | 先说明目标、涉及文件和影响，取得用户明确确认后再执行。 |
| 改写已有长期规则、解决相互冲突的规定               | 向用户提出具体取舍并确认；不得静默覆盖。               |
| Git 提交、打标签、重置、暂存全部文件或批量清理     | 不属于默认初始化步骤；只有用户明确授权才执行。         |

需要确认时优先使用当前 Agent 的原生提问功能；不可用则直接提问。用户未答复时不执行该项操作；其他独立且安全的部分可以继续。

## 四、创建基础结构

### 4.1 标准骨架

**首次创建 Docs** 时，使用统一的初始骨架；没有实际内容的模块只放 `index.md`，不制造正文。**已有 Docs** 不因骨架不同就强制全量重建。

```text
<项目根目录>/
├── AGENTS.md
└── docs/
    ├── index.md
    ├── project/index.md
    ├── design/index.md
    ├── pending/index.md
    ├── evidence/index.md
    ├── rules/index.md
    ├── knowledge/index.md
    └── inbox/index.md
```

- 模块目录采用上述固定英文名称；普通内容文档**优先使用中文名称**，专业术语及约定的特殊名称除外。
- 每个知识内容目录以 `index.md` 作为入口；有实际子主题时再建立子目录，不预先创建空分类树。
- 不要求七个模块都填充正文；已有项目允许保留不冲突的原有目录和文档位置。

### 4.2 写好索引，而不是只建立空目录

创建或补充 `docs/index.md`：说明它是当前项目的 Docs 总入口，列出**实际存在**的模块和重要现有资料入口。不要把插件级原则全文复制进来。

创建或补充各知识目录 `index.md`：

- 说明当前目录用途；有内容则提供实际链接。
- 每个导航条目表达**内容摘要**与**使用场景**，不能只写文件名；两者不要重复。
- 空模块可以写“暂无内容”，不添加虚假链接；已有资料暂时留在其他位置时，可以从相关索引链接过去并标明其用途。
- 对已有文档的相对链接，按文件真实位置计算；不能为了让链接好看而复制或迁移资料。

示例（仅用于说明导航条目，不要求固定格式）：

```markdown
- [模块关系与代码入口](project/模块关系与代码入口.md)：介绍核心模块职责和调用关系；定位实现或评估改动范围时阅读。
```

### 4.3 接入 `AGENTS.md`

先检查项目根目录的 `AGENTS.md`：

- **不存在：** 创建最小导航入口。
- **已存在：** 只增补或修正 Docs 入口，保留现有有效指令；已有等效入口时不要重复添加。
- **存在子工程 AGENTS.md：** 保留其原有职责，按实际适用范围处理，不以根目录规则无条件覆盖。

最小导航片段：

```markdown
## 项目知识

本项目使用 [Docs](docs/index.md) 作为人和 AI 共享的项目知识工作区。
执行相关任务时，从索引按需查阅项目知识及适用规则；结合代码、配置和实际结果核实事实，不必一次阅读全部文档。
```

**不要**把全部模块介绍、索引条目、插件级 `principles.md` / `init.md` / `maintain.md` 复制进 `AGENTS.md`。


### 4.4 为已有代码建立 Project 知识映射

对于已有实际实现的项目，应依据 [Project 内容规格](spec.md) 建立或完善 Project 知识映射，使人和 AI 能够从整体到局部理解当前项目，并定位实际代码。

**初始化应以项目真实内容的有效覆盖为目标，不以生成项目概览或建立目录骨架作为完成条件。**

#### 1. 调查项目现状

结合现有文档、代码、配置和必要的验证，识别：

* **项目定位：** 项目用途、主要能力、系统边界及外部依赖。
* **整体组成：** 工程、子系统、主要模块及职责划分。
* **功能与行为：** 主要业务功能、处理流程及关键运行机制。
* **协作与关系：** 重要调用关系、数据流、依赖关系、并发与异步处理、失败处理等实际存在的机制。
* **代码组织：** 重要目录、程序入口、关键实现位置及逻辑功能与代码的对应关系。
* **当前状态：** 实际能力、已知限制、停用功能及需要特别注意的行为。

根据项目实际特点选择调查重点，不要求所有项目具备相同的技术组成。

调查不能仅停留在根目录结构、程序入口和单条主业务链路，应覆盖能够代表项目主要能力与运行方式的功能和机制。

#### 2. 检查已有知识

阅读现有 Project 文档及其他可信资料，对照实际实现判断：

* 哪些内容已有准确、可用的描述。
* 哪些主要功能、模块或运行机制尚未覆盖。
* 哪些内容存在过时、错误或与代码不一致的情况。
* 哪些资料可以直接复用或通过索引引用。

优先补充和修正现有知识，不为统一文件名或结构重复创建文档。

#### 3. 建立分层知识映射

根据调查结果组织 Project 内容：

1. 通过 `project/index.md` 建立整体认知和逐层深入的导航。
2. 描述项目的主要组成、职责、能力及重要关系。
3. 对主要功能和关键运行机制建立可理解的说明，必要时使用流程图、结构图或关系图。
4. 建立功能、模块与实际代码路径之间的对应关系。
5. 对内容复杂、具有独立理解价值的主题建立下级文档，并通过索引关联。
6. 对已有知识进行修正、补充与整合，避免重复维护相同事实。

**文档如何拆分由项目复杂度决定，信息是否需要描述由实际项目决定。**

不要求逐行解释代码或机械复制全部文件目录，但不能以避免文档增长为由省略主要功能、关键机制或重要关系。

#### 4. 检查知识覆盖

完成初步建设后，对照调查结果检查：

| 检查项     | 完成要求                                       |
| ---------- | ---------------------------------------------- |
| 项目整体   | 能理解项目用途、主要能力及系统边界             |
| 组成与职责 | 主要工程、子系统和模块有明确说明               |
| 功能与行为 | 主要功能及关键运行机制有可用的知识入口         |
| 协作关系   | 影响系统理解的重要调用、依赖及数据关系得到表达 |
| 代码定位   | 能从主要功能定位到真实代码路径和关键入口       |
| 当前状态   | 实际能力、重要限制与停用内容得到准确区分       |
| 分层导航   | 能通过索引从整体逐步深入相关内容               |

上述检查关注**主要知识是否得到有效覆盖**，不要求所有细节都独立成文，也不以文档数量或篇幅判断质量。

#### 5. 处理未覆盖内容

对于规模较大或认识尚不充分的项目：

* 不得编造未经核实的实现细节。
* 对暂未覆盖的功能和机制，明确记录其范围与原因。
* 区分已完成的知识映射与仍需补充的部分。
* 必要时将明确需要继续调查的内容列入 Pending。
* 不得将仅完成项目概览或部分模块调查的结果宣称为完整的 Project 知识映射。

初始化可以分阶段推进，但应明确当前覆盖范围，避免遗漏被误认为完成。

**最终目标：建立与项目实际复杂度相匹配、能够帮助人和 AI 理解项目及定位代码的初始知识映射。**

### 4.5 补充默认 Rules

检查是否已有同类代码注释约定。不存在且无明显冲突时，创建 `docs/rules/代码注释规范.md`；存在则优先沿用，冲突时先询问用户。

默认内容：

```markdown
# 代码注释规范

- 代码注释优先使用简洁、准确的中文。
- 专业术语、API、类名、变量名、协议名称等可保留原文。
- 注释主要说明意图、约束和不直观的行为，避免重复代码字面意思。
- 不强制批量翻译既有英文注释；受外部格式或更具体规范约束时遵循相应要求。
```

创建后在 `docs/rules/index.md` 中注明“编写或修改代码注释时阅读”。**初始化不应顺带修改源码中的注释。**

### 4.6 配置 Evidence 的临时材料边界

确保 `docs/evidence/index.md` 是可查阅的固定入口。对于 Git 项目，按**实际仓库根目录**检查 `.gitignore`，必要时追加等效规则，使 Evidence 临时材料默认不入库，同时保留索引。例如当 `docs/` 位于仓库根目录时：

```gitignore
/docs/evidence/*
!/docs/evidence/index.md
```

已有 Git 跟踪的材料不会因此自动取消跟踪；**不要借初始化执行 `git rm --cached`、删除旧证据或清理其他临时文件**。非 Git 项目不创建无效的 Git 配置。

## 五、已有项目的接入原则

遇到已有 `docs/`、子工程文档、需求资料或历史记录时，按下面的顺序处理：

1. **先确认用途。** 阅读必要内容，区分当前项目说明、设计资料、参考文档、临时证据与历史记录；不凭文件名或目录位置直接判定。
2. **优先保留原位。** 已有内容仍可使用时，通过 `docs/index.md` 或相关模块索引添加导航；即使文件暂时不在标准模块目录，也不妨碍初始化完成。
3. **只补真正缺少的内容。** 缺少导航则补索引；缺少真实项目入口则补 Project 概览；不强迫每份旧资料立刻“归位”。
4. **冲突单独处理。** 对重复、过时、相互矛盾或归属不明的内容，先标识并提出建议；未经确认不合并、删除或迁移。
5. **不改写历史当作当前事实。** 如 `PROJECT_MEMORY.md` 等历史记录，可以作为参考来源或建立导航，不直接视为现行项目规范，也不因迁移而批量改写历史正文。

**初始化的目标是让现有知识可达、当前项目可理解，不是重排仓库。**

## 六、验收与结束

执行完成后逐项核对：

| 验收项   | 通过条件                                                                                |
| -------- | --------------------------------------------------------------------------------------- |
| 入口     | `AGENTS.md` 能引导到当前项目的 `docs/index.md`，原有指令未丢失。                    |
| 导航     | 实际知识目录有索引，新增导航链接有效，条目有内容摘要和使用场景。                        |
| 可理解性 | 已有代码的项目能通过 Project 入口了解主要组成、职责及代码位置；无代码项目没有虚构实现。 |
| 存量资料 | 已有有效资料仍可访问，没有未经授权的迁移、覆盖或删除。                                  |
| 初始约定 | 默认代码注释规则已创建或与现有规则核对；Evidence 临时材料处理方式明确。                 |
| 改动范围 | 只修改本次初始化所需内容；未擅自 Git 提交、打标签或清理仓库。                           |

最后简短报告**新增/修改了什么、复用了什么、哪些事项尚待用户决定**。无法完成的项目说明具体阻碍，不伪称已通过验收。

**满足目标即停止。** 不追加全面文档迁移、全量代码解读、知识提炼或日常 Docs 维护任务。
