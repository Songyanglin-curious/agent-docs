## 二、初始化时执行什么

### 2.1 新项目

用户明确要求初始化后，按顺序执行：

1. 读取项目 AGENTS.md、已有资料入口及适用配置，确认项目根目录和已有改动。
2. 创建缺失的 docs/index.md 以及 project/、design/、rules/、knowledge/ 四个目录和各自的 index.md。
3. 根索引为四个直接子目录提供链接、内容范围和查找用途；空目录只说明用途和暂无内容，不制造正文。
4. 在 AGENTS.md 增补 docs/index.md 总入口；已有等效入口则复用。验证材料位置按 2.3 约定，其他 Docs 外资料按 4.3 选择入口，不逐文件登记到 AGENTS.md。
5. 有代码时依据实现建立 Project 内容与代码导航；不以骨架完成代替实现调查，不虚构能力，不强制拆成大量文件。
6. 核对现有代码注释约定，并按 2.3 确定验证材料位置。
7. 从 AGENTS.md 检查本次新建入口链，报告实际覆盖范围后结束。

不预建待办、收集箱、环境问题文件，也不预建相应目录或空证据目录。

### 2.2 已有项目

先读已有入口，复用有效内容和目录，只补当前接入需要的缺口。旧 pending/、inbox/、docs/evidence/ 保留并继续提供有效导航，不因新骨架变化搬迁、合并、删除或取消 Git 跟踪。目录重组另按明确授权执行。

### 2.3 验证材料位置

1. 检查已有测试输出、CI 附件、实验产物约定，存在则复用。
2. 无约定时，拟采用项目根目录的 evidence/（即 <项目根目录>/evidence/，不在 docs/ 下）；初始化只记录位置，实际保存材料时创建。
3. 在 AGENTS.md 登记入口、用途和存放约定；详细规定已有文件时链接原文，不重复复制。
4. 先核对已有 Git 约定和材料的保留用途，仅对已明确为临时产物的路径或模式补充忽略规则。不因采用默认存放位置就直接忽略整个根目录 evidence/，也不统一强制各项目使用相同的 Git 策略。
5. 需要共享或长期追溯的材料允许纳入版本管理。不确定保留需求时，保持材料和跟踪状态不变，必要时集中确认；不得自行删除、取消跟踪或新增会排除这些材料的忽略规则。
6. 不移动或清理旧证据，不执行 git rm --cached。正式测试及夹具仍在工程中，文档必要配图仍随文档保存。

## 三、一轮结束时如何维护

### 3.1 执行顺序

以下用于核对拟保留的操作行为，不要求用新流程替换当前 Maintain 正文。实施时保留现有章节和判断顺序，只在与新落点、导航或规则积累冲突的条目上修改。

1. 用户本轮要求不维护 Docs，或当前 cwd 没有 docs/index.md：直接结束，不初始化、不向上寻找其他项目。
2. 根据本轮已知变化按下表筛选，没有对应变化就跳过，不遍历所有目录。
3. 有变化时从索引定位目标，重读相关文档及直接父级索引；有必要才核对实现和验证结果。
4. 现有内容准确则不写；需要改时优先更新原文，再按第四节维护导航。
5. 检查本轮影响范围，简述实际修改后结束。不生成检查报告，不输出所有模块的无变化清单。

### 3.2 情况与动作

| 触发条件 | 读写位置 | 写什么或何时跳过 |
| --- | --- | --- |
| 实现变化影响已描述的能力、行为、结构、关系、限制或位置 | Project 对应主题 | 更新实际情况与必要代码路径；未验证写明未验证；不等验收通过才同步。无认知影响的实现细节跳过 |
| 形成可独立理解的需求、方案、决定、未决问题，或已有设计依据变化 | Design 对应主题 | 写内容、依据和当前状态，区分探索与决定；零散讨论尚无可保存结果时跳过 |
| 用户确立长期约定，或同一项目多次纠正已明确体现稳定偏好 | Rules 对应主题 | 按 3.3 核对依据，写适用场景、范围、要求；稳定且不冲突的项目约定可直接提炼；一次性指令不升级 |
| 得到值得以后理解、学习或复用的知识经验 | Knowledge 或已有主题 | 写必要背景、认识和条件；未证实认识注明不确定性，不全量保存排错过程 |
| 确有需要跨会话延续的行动 | 先用已有任务入口；无合适入口才用 docs/待办.md | 写事项、下一步或阻碍、原文链接；本轮已完成或未决定实施时不创建 |
| 有值得保留而暂不能分类的内容 | 已有收集入口，必要时 docs/收集箱.md | 保存可理解内容与来源，不收录全部对话 |
| 环境异常或处理办法影响后续工作 | 优先现有部署说明或相关主题，必要时 docs/环境问题.md | 写现象、适用环境、已确认处理办法或当前阻碍，不强制另建文件 |
| 产生测试、实验、审查原始材料 | 执行验证时按 AGENTS.md 约定保存 | Maintain 只利用已有结果更新事实与限制，不扫描、整理或清理证据目录 |

表中单文件都是可选落点。优先复用已有主题，不重复创建。规模、独立性或查找需要确实要求拆分时，再建子目录和索引。待办完成或取消后更新或移除行动条目，有价值的背景在相关主题保留，不另建完成历史库。

### 3.3 Rules 如何积累

| 情况 | 动作 |
| --- | --- |
| 用户明确提出长期约定 | 直接写入或更新 Rules，不重复确认 |
| 同一项目中，多次纠正或连续协作明确体现稳定偏好 | 可以主动提炼为当前项目约定；核对相关纠正及适用场景，保持用户表达的要求程度，不重复询问 |
| 一次性指令，或只与本次任务有关的选择 | 不升级为长期规则 |
| 经验尚不稳定，或只有 AI 的推测 | 有保存价值时写入 Knowledge 或原主题，注明条件和不确定性 |
| 新提炼与现行规则冲突、用户意图不清，或需要扩大适用范围 | 说明具体取舍，确认后再变更或扩大；不静默覆盖 |

提炼稳定偏好时，先阅读已有相关规则，确认没有等效内容或冲突，再在原主题更新，必要时新建。写清场景、项目范围、要求及必要的来源线索；不得仅凭重复次数臆造约束，不把偏好加重成强制要求。修改后简述实际提炼内容，方便用户纠正，不另设审批步骤。

不建立候选规则库或审批文件；项目内形成的规则不自动推广到其他项目。用户后续修正或取消时，更新原规则，不保留互相矛盾的有效要求。

Rules、Knowledge 保留理解所需的来源、条件和适用范围；本次不实现跨项目同步或融合系统。

## 四、索引具体怎么写、怎么改

### 4.1 条目最低要求

每个条目回答：**这里有什么、什么时候找它、入口在哪里。** 用自然句表达，不要求统一字段表格。例如：

```markdown
- [流式通信](流式通信/index.md)：SSE 事件、断线与取消行为；排查事件解析或流中断时阅读。
```

上面是格式示例，不是本项目实际资料链接；正式索引只能使用真实入口。只写“相关资料”“技术文档”无法区分去向，须改成实际范围与用途。未实现、待验证等信息影响导航判断时应保留。

### 4.2 Docs 内新增或修改内容

1. 读取被改文档和直接父级 index.md；要概括子目录时读取该子目录 index.md，不足以判断再查必要正文，不扫描全库。
2. 在直接父级增加或修正子文件条目。新增子目录时创建其 index.md，并让父级链接该 index.md。
3. A 下有五个子目录，A/index.md 就登记五个子目录入口，分别概括范围和用途；不复制五份子索引正文，不展开孙级文件清单。
4. A 的父级仅概括 A 的整体范围与用途并链接 A/index.md，不再展开那五个目录。更上层同样处理。
5. 沿本次受影响的父级链检查：范围、用途、核心能力或重要边界变了才改摘要；只是下层细节增加且摘要仍准确，不逐级重写。
6. 确认该链已从 docs/index.md 接通；新增链每一级都要有入口。修复必要缺口，不借机整理其他目录。

父级概括示例：“内部 AI 接入：鉴权、工具协商与流式交互；接入开发或联调时阅读。”事件字段、详细步骤留在下层。概括以实际内容为依据，不能把候选方案写成已实现能力。

### 4.3 Docs 外内容

1. 先判断资料用于项目级长期查找，还是只服务某个文档主题，按下表登记。核心要求是从 AGENTS.md 的重要入口可以继续找到，而不是所有外部文件都直接列在 AGENTS.md。

| 外部内容 | 登记位置 |
| --- | --- |
| 稳定、长期使用的资料目录或项目级重要独立入口 | AGENTS.md 登记集合入口及用途，已有入口则复用 |
| 某个 Design 或其他具体主题使用的需求原件、契约、参考文件 | 在该主题文档链接原件，通过 AGENTS.md → docs/index.md → 主题文档找到，不再逐项登记 AGENTS.md |
| 临时日志、截图、测试输出 | 按 2.3 的统一证据位置查找，不逐文件登记 |

2. 资料集合优先指向已有目录说明或集合入口，不新建一套重复索引。没有任何已知入口的必要资料，补充对应集合入口或相关主题引用，避免成为孤立文件。
3. 存放目录尚未创建时，注明路径和“有材料时创建”，不伪造已有可读文件链接。
4. 不复制资料正文或 Docs 文件树进 AGENTS.md；AGENTS.md 只提供重要入口和必要指引，Docs 内部仍通过 docs/index.md 查找。

例如：“验证材料保存于项目根目录的 evidence/（有材料时创建），用于查看本机测试日志与截图。”已有详细约定时链接实际规范文件。

### 4.4 删除、移动或改名

只有取得相应授权才执行。同步直接父级索引、本次已知引用和受影响父级摘要；删除失效入口、修正新路径，不能只改文件不改导航。

### 4.5 怎么判断本次索引维护完成

- 从 docs/index.md 能逐层进入本次变更的 Docs 内容；Docs 外资料能从 AGENTS.md 的入口继续找到。
- 每层只索引直接子级，没有复制下层全文或递归列出全部后代。
- 用实际查找问题阅读条目，能判断下一步进入哪里；多个入口相近时描述能区分范围。
- 入口、摘要和状态符合实际内容。链接有效只是最低检查，不代表描述正确。

以上用于核对结果，不要求生成索引检查报告。

## 五、实施核验怎么做

实施结束时，按用户当前要求、已确认 Design 或其他有效依据核对本次范围，简要区分已实现且已验证、已实现未验证、未实现或受阻。

不要求先写 Design，不复制 Spec，不强制生成拆分清单。复杂任务由 AI 自行安排步骤；确需跨会话交接时才按第三节保留必要内容。候选设计不等于已获实施授权。

Maintain 使用已有核验结果维护事实与限制；Stop Hook 不接管开发，不扩大测试范围，不为完成清单反复续接。

## 六、审核后如何落地

1. 按第一节调整四份源规则，再同步 README 及当前实现说明；Maintain 逐处局部修订，不整体重写稳定流程，不批量迁移已有项目。
2. 检查四份规则是否仍要求七模块、固定 Pending／Inbox 或 Docs 内新 Evidence；修正矛盾的步骤、示例和引用。存量兼容与历史说明可保留旧名称。
3. 在临时项目检查：四目录初始化；按需文件加入后逐层可达；外部集合接入 AGENTS.md、主题参考在主题内可达、日志不逐个登记；下层细节变化不重写全部父级；已有项目不自动迁移；无变化不创建文件。另检查稳定项目偏好可以主动提炼、一次性指令不升级、冲突与范围扩大不自动生效，以及证据保留需求不明时不改变跟踪状态。
4. 若后续授权包含打包安装，再执行现有构建、测试与归档检查，核对双端包内四份规则。自动测试与模型语义验收分别说明。
5. 源码变化不会自动覆盖本机用户规则。同步本机时先定位实际 rulesDir／环境变量，备份并核对四份文件。同步、发布、安装按届时明确范围执行，不在预案审核期间操作。

当前 Hook 未硬编码七模块，本稿不要求改触发机制。保留 Project 实际实现调查与代码导航的深度，不把本次做减法变成删减项目认知。

## 七、请审核的具体取舍

| 取舍 | 本稿建议 |
| --- | --- |
| 默认目录 | 仅 Project、Design、Rules、Knowledge |
| 其他上下文 | 优先已有主题，无合适入口再用单文件并登记索引 |
| 证据位置 | 复用现有约定，否则项目根目录 evidence/，实际产生时创建 |
| 导航 | Docs 内根索引逐层可达；AGENTS.md 只列重要外部入口，主题资料由主题引用，证据按统一目录查找；逐层概括直接子级 |
| Rules 积累 | 明确长期约定直接维护，多次纠正体现的稳定项目偏好可以主动提炼；一次性指令不升级，冲突与范围扩大需确认 |
| Maintain 改动 | 保留稳定机制，仅修改受本次职责与落点调整影响的条目 |
| 证据 Git 策略 | 按项目实际约定区分临时与追溯材料，不直接整目录忽略，不明确时保持文件与跟踪状态 |
| 现有项目 | 不自动搬迁、清理或重建 |

后续修订以现行源规则为准；源码修改不等于本机用户规则和运行会话已升级，仍按实际范围单独同步和验收。
